## 2. Постановка задачи и контекст

1. **Предметная область и задача:**
   - Задача: прогнозирование ежедневных продаж нефти (условный временной ряд).
   - Пользователь: аналитик/менеджер, которому нужно получить прогноз на ближайший месяц для планирования.

2. **Формулировка задачи в терминах ML/ИИ:**
   - Вход: история значений продаж `history` (список float) за предыдущие дни.
   - Выход: прогноз `forecast` на горизонт `H=30` дней.
   - Требования/ограничения:
     - сервис должен быстро отвечать на запрос;
     - `/predict` обязан использовать реальную обученную модель (а не заглушку);
     - прогнозируемые значения не должны быть отрицательными (в коде реализован `clip >= 0`).

3. **Целевые метрики качества:**
   - Используются **MAE** и **RMSE**.
   - Причина выбора: это стандартные регрессионные метрики, которые понятны для интерпретации ошибок в единицах целевой переменной.

## 4. Модели и подходы

1. **Базовые (baseline) модели:**
   - Naive: прогноз = последнее значение.
   - Seasonal naive (period=7): повторение значения недельной давности.
   - Moving average (window=7): среднее последних 7 дней.

2. **Улучшенная модель:**
   - Финальная модель: **lag-features (L=60) + StandardScaler + Ridge** (sklearn).
   - Мультишаговый прогноз делается рекурсивно: модель обучена предсказывать 1 шаг вперёд, затем предсказание подставляется в историю, и так 30 раз.

3. **Нейросетевые модели:**
   - В проекте не использовались (уровень [BASIC], акцент на baseline’ы и аккуратный протокол).

## 5. Экспериментальный протокол и результаты

1. **Экспериментальный протокол:**
   - Разбиение строго по времени:
     - train = первые 70%
     - val = следующие 15%
     - test = последние 15%
   - Оценка делалась через rolling backtest с шагом `stride=7` и горизонтом `H=30`.

2. **Сравнение моделей по метрикам:**

   Итоговые метрики (из запуска `scripts/train_model.py`, также сохранено в `artifacts/metrics.json`):

   | Модель / конфигурация              | Split | MAE   | RMSE  | Комментарий |
   |-----------------------------------|-------|-------|-------|-------------|
   | Naive                              | val   | 7.964 | 9.743 | простой baseline |
   | Seasonal naive (7)                 | val   | 4.029 | 5.250 | сильный baseline при недельной сезонности |
   | Moving average (7)                 | val   | 4.461 | 5.684 | сглаживание |
   | Ridge + lag(60) + recursive (финал)| val   | 2.978 | 4.113 | лучший результат |
   | Naive                              | test  | 6.995 | 8.386 | простой baseline |
   | Seasonal naive (7)                 | test  | 3.629 | 4.615 | сильный baseline |
   | Moving average (7)                 | test  | 4.410 | 5.424 | сглаживание |
   | Ridge + lag(60) + recursive (финал)| test  | 2.611 | 3.419 | лучший результат |

3. **Выбор финальной модели:**
   - Выбрана модель **Ridge + lag(60)**, т.к. она показывает лучшие MAE/RMSE и на val, и на test по сравнению с baseline’ами.
   - Trade-off: модель чуть сложнее baseline’ов, но остаётся простой, быстрой и легко интегрируется в сервис.

## 6. Архитектура решения и сервис

1. **Архитектура пайплайна:**
   - `scripts/generate_data.py` → создаёт `data/raw/oil_sales_synth.csv`
   - `scripts/train_model.py` → обучает модель и сохраняет артефакты в `artifacts/`
   - FastAPI сервис при старте загружает `artifacts/model.pkl` и `artifacts/meta.json`
   - `/predict` получает `history` и возвращает прогноз на `horizon` дней

2. **API и endpoints:**
   - `GET /health`: статус сервиса + флаг загрузки модели + версия
   - `POST /predict`:
     - вход: `history: list[float]`, `horizon: int (1..30, default=30)`
     - выход: `forecast: list[float]` длиной `horizon`, `model_version`

3. **Технологический стек:**
   - Python 3.12
   - pandas/numpy, scikit-learn, joblib
   - FastAPI + uvicorn
   - Docker для воспроизводимого запуска

## 8. Ограничения и дальнейшая работа

Ограничения:
- данные синтетические и не отражают реальные бизнес-факторы (цены, логистика, ограничения добычи/транспортировки);
- модель использует только прошлые значения ряда (без внешних признаков).

Что можно улучшить:
- добавить экзогенные признаки (цены, календарные фичи, события);
- попробовать модели временных рядов (ETS/SARIMAX) или градиентный бустинг по лагам;
- добавить доверительные интервалы прогноза.
